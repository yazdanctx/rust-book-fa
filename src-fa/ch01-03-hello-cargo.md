کارگو در واقع ابزار اصلی `Rust` برای ساختن پروژه‌ها (`build`) و مدیریت پکیج‌هاست و مثلا میاد کدت رو بیلد میکنه یا لایبری هایی که پروژه ات لازم داره رو دانلود میکنه.

به این لایبری هایی هم که پروژه ات نیاز داره میگیم`dependencies`.

برنامه‌های خیلی ساده‌ `Rust` مثل همون `Hello, world!` که نوشتیم که اصلا `dependency` ندارن و اگه همون پروژه رو با `Cargo` می‌ساختیم، `Cargo` فقط از قابلیت `build` کردنش استفاده می‌کرد و کار خاص دیگه‌ ای نداشت.

ولی وقتی پروژه‌هات بزرگتر بشن، احتمالا کلی لایبری اضافه میکنی و اون موقعس که کارگو خیلی کار رو راحت تر می‌کنه چون مدیریت این `dependency`ها رو میاد خودش انجام میده.

### این کتاب با `Cargo` پیش میره

چون تقریبا اکثر پروژه‌ های `Rust` از `Cargo` استفاده می‌کنن، منم از اینجا به بعد این کتاب هم فرض میکنم که تو داری با `Cargo` کار میکنی.

اگه `Rust` رو با `installer` رسمی که بهت گفتم نصب کرده باشی، الان `Cargo` هم همراهش نصب شده.

ولی اگه `Rust` رو یه روش دیگه نصب کردی، میتونی چک کنی `Cargo` داری یا نه.

داخل ترمینال بزن:

```console
$ cargo --version
```

اگه یه چیزی مثل شماره ورژن دیدی:

```text
cargo 1.89.0
```

یعنی `Cargo` نصب شده و همه چی اوکیه.

ولی اگه اروری مثل این دیدی:

```text
command not found
```

یعنی `Cargo` نصب نیست و باید ببینی چطوری `Cargo` رو جدا نصب کنی.

### ساخت یک پروژه با `Cargo`

بیاید با استفاده از `Cargo` یه پروژه جدید بسازیم و ببینیم چه فرقی با پروژه قبلی `Hello, world!` داره.

الان برگرد به دایرکتری `projects` ( یا هرجایی که کدتو گذاشتی ) و بعد این کامند هارو اجرا کن:

```console
$ cargo new hello_cargo
$ cd hello_cargo
```

دستور اول یه دایرکتری جدید و یه پروژه به اسم `hello_cargo` میسازه، ما اسم این پروژمون رو `hello_cargo` گذاشتیم و کارگو فایل های پروژه رو داخل یه دایرکتری با همین اسم ایجاد میکنه.

برو داخل دایرکتری `hello_cargo` و فایل هاش رو لیست کن. میبینی که `Cargo` خودش دو تا فایل و یه دایرکتری برامون ساخته:

- یه فایل به اسم `Cargo.toml`
- یه دایرکتری به اسم `src` که داخلش یه فایل `main.rs` قرار داره.

همچنین یه ریپازیتوری جدید گیت رو هم `initialize` کرده و یه فایل گیت ایگنور هم ساخته.

البته اگه دستور `cargo new` رو داخل یه ریپازیتوری گیت که از قبل وجود داره ران کنی، فایل های گیت ساخته نمیشن.

حالا فایل `Cargo.toml` رو با ادیتوری که دوست داری باز کن. باید یه چیزی مشابه این باشه:

<span class="filename">نام فایل: Cargo.toml</span>

```toml
[package]
name = "hello_cargo"
version = "0.1.0"
edition = "2024"

[dependencies]
```

<span class="caption">لیستینگ ۱-۲: محتوای فایل `Cargo.toml` که توسط `cargo new` ساخته شده</span>

این فایل با فرمت [TOML](https://toml.io) (`Tom’s Obvious, Minimal Language`) نوشته شده و این کارگو کلا از همین فرمت برای تنظیمات خودش استفاده میکنه.

خط اول یعنی `[package]` ، یه `section` رو مشخص میکنه که یعنی تنظیمات بعدی مربوط به یه پکیج هستن.

سه خط بعدی اطلاعاتی رو تنظیم میکنن که کارگو برای کامپایل کردن برنامه نیاز داره:

- اسم پروژه
- ورژن پروژه
- ادیشن مورد استفاده `Rust`

در مورد کلید `edition` توی [Appendix E](https://doc.rust-lang.org/book/appendix-05-editions.html) بیشتر صحبت میکنم.

خط آخر، یعنی `[dependencies]`، برای لیست کردن `dependency`های پروژه‌ست. توی `Rust` به پکیج‌ های کد `crate` گفته می‌شه.

ما برای این پروژه به `crate` دیگه‌ای نیاز نداریم، ولی توی اولین پروژه‌ی فصل ۲ به `crate` های دیگه نیاز پیدا می‌کنیم، برای همین اونجا از این بخش `dependencies` استفاده می‌کنیم.

حالا فایل `src/main.rs` رو باز کن و یه نگاه بهش بنداز:

<span class="filename">نام فایل: src/main.rs</span>

```rust
fn main() {
    println!("Hello, world!");
}
```

کارگو خودش یه برنامه‌ی `Hello, world!` برات ساخته دقیقا مثل همونی که توی لیستینگ ۱-۱ خودمون نوشتیم!

تا اینجا تنها تفاوت‌های پروژه‌ی ما با پروژه‌ای که کارگو ساخته اینه که کارگو اومده کد رو داخل دایرکتری `src` گذاشته و یه فایل `Cargo.toml` هم داخل دایرکتری اصلی پروژه ساخته.

کارگو انتظار داره فایل‌های سورس پروژه داخل دایرکتوری `src` قرار داشته باشن. دایرکتوری اصلی پروژه فقط برای چیزهایی مثل فایل‌های `README`، اطلاعات لایسنس، فایل‌های تنظیمات و هرچیزی که مربوط به کد نیست استفاده میشه.

الان داری میبینی که کارگو داره کمک میکنه پروژه ات مرتب‌ تر بشه و هرچیزی جای خودش رو داره و همه‌ چیز رو گذاشته سر جای خودش.

بعد اینکه اگه یه پروژه رو بدون کارگو شروع کرده باشی ( مثل همون پروژه‌ی `Hello, world!` که قبلا ساختیم )، می‌تونی بعدا به یه پروژه‌ ای تبدیلش کنی که از `Cargo` استفاده می‌کنه.

کافیه کد پروژه رو ببری داخل دایرکتوری `src` و یه فایل مناسب `Cargo.toml` هم بسازی و تمام.

یه راه ساده برای ساختن فایل `Cargo.toml` هم اینه که دستور `cargo init` رو اجرا کنی و این کامند خودش فایل رو به صورت خودکار برات میسازه.

### اجرای پروژه ای که با `Cargo` ساخته شده

حالا بیا ببینیم وقتی برنامه `Hello, world!` رو با `Cargo` بیلد و اجرا میکنیم، چه فرقی داره.

از داخل دایرکتوری `hello_cargo` این دستور رو اجرا کن تا پروژه بیلد بشه:

```console
$ cargo build
   Compiling hello_cargo v0.1.0 (file:///projects/hello_cargo)
    Finished dev [unoptimized + debuginfo] target(s) in 2.85 secs
```

این دستور، به جای اینکه فایل اجرایی رو داخل دایرکتوری فعلی بسازه، اون رو داخل مسیر `target/debug/hello_cargo` (یا توی ویندوز `target\debug\hello_cargo.exe`) قرار می‌ده.

چون به صورت دیفالت یه `debug build` ساخته می‌شه و `Cargo` فایل اجرایی (منظورم همون فایل باینریه) رو داخل دایرکتوری `debug` می‌ذاره.

برای اجرای برنامه، این کامند رو بزن:

```console
$ ./target/debug/hello_cargo # or windows: .\target\debug\hello_cargo.exe
Hello, world!
```

اگه همه‌ چی درست پیش رفته باشه، عبارت `Hello, world!` توی ترمینال بالا میاد.

بعد اینکه اولین باری که شما `cargo build` رو اجرا می‌کنی، `Cargo` یه فایل جدید هم توی دایرکتوری اصلی پروژه می‌سازه به اسم `Cargo.lock`.

این فایل نسخه دقیق `dependency`های پروژه رو نگه میداره.

حالا از اونجایی که این پروژه هنوز هیچ `dependency`ای نداره، محتوای این فایل خیلی کم و سادس.

و نکته مهم اینکه شما هیچ وقت لازم نیست خودت این فایل رو دستی تغییر بدی و `Cargo` خودش محتوای این فایل رو مدیریت میکنه.

خب ما تا اینجا پروژه رو با `cargo build` بیلد کردیم و بعد با `./target/debug/hello_cargo` اجراش کردیم.

ولی یه راه راحت‌ تر هم هست و شما می‌تونی از `cargo run` استفاده کنی تا هم کد کامپایل بشه و هم برنامه با یه دستور اجرا بشه.

```console
$ cargo run
    Finished dev [unoptimized + debuginfo] target(s) in 0.0 secs
     Running `target/debug/hello_cargo`
Hello, world!
```

استفاده از `cargo run` خیلی راحت‌ تره چون لازم نیست یادت بمونه اول `cargo build` رو اجرا کنی و بعد مسیر کامل فایل اجرایی رو بنویسی و به خاطر همین بیشتر دولوپرا از `cargo run` استفاده میکنن.

دقت کن که این سری اون مسجی که نشون میده کارگو داره `hello_cargo` رو کامپایل می‌کنه، ندیدیم.

کارگو خودش فهمید که فایلای پروژه تغییری نکردن پس دوباره بیلدشون نکرد و مستقیم همون فایل اجرایی قبلی رو ران کرد.

اما اگه سورس کدت رو تغییر داده بودی، کارگو میومد قبل اجرا دوباره پروژه رو بیلد می‌کرد و خروجی چیزی شبیه این میشد:

```console
$ cargo run
   Compiling hello_cargo v0.1.0 (file:///projects/hello_cargo)
    Finished dev [unoptimized + debuginfo] target(s) in 0.33 secs
     Running `target/debug/hello_cargo`
Hello, world!
```

بعد این کارگو یه دستور دیگه هم داره به اسم `cargo check`.

این دستور فقط خیلی سریع بررسی میکنه که کدت بدون مشکل کامپایل میشه یا نه، ولی فایل اجرایی تولید نمیکنه.

```console
$ cargo check
   Checking hello_cargo v0.1.0 (file:///projects/hello_cargo)
    Finished dev [unoptimized + debuginfo] target(s) in 0.32 secs
```

شاید بپرسی که این اصلا به چه دردی میخوره؟؟

چون `cargo check` معمولا خیلی سریع تر از `cargo build` هست و دلیلش هم اینه که مرحله ساخت فایل اجرایی رو کامل رد میکنه.

اگه شما موقع کدنویسی مدام داری تغییراتی که دادی رو چک میکنی، `cargo check` سریع میتونه بهت بگه که پروژه هنوز بدون خطا کامپایل میشه یا نه.

به خاطر همین، خیلی از دولوپر ها موقع نوشتن کد هر چند وقت یبار `cargo check` رو اجرا میکنن تا مطمئن بشن همه چیز اوکیه و بعد حالا هر وقت بخوان خود برنامه رو ران کنن میان از `cargo build` استفاده میکنن تا فایل اجرایی ساخته بشه.

بیا یه مرور کنیم ببینیم تا اینجا چی یاد گرفتیم:

- با `cargo new` میتونیم یه پروژه جدید بسازیم.
- با `cargo build` میتونیم یه پروژه رو کامپایل کنیم.
- با `cargo run` میتونیم پروژه رو بیلد کنیم و همون موقع هم اجراش کنیم.
- با `cargo check` میتونیم بدون ساختن فایل اجرایی، فقط بررسی کنیم که کد بدون خطا کامپایل میشه یا نه.
- به جای اینکه خروجی بیلد کنار فایل های پروژه ذخیره بشه، کارگو اون رو داخل دایرکتری `target/debug` نگه میداره.

یه مزیت خوب کارگو هم اینه که همه دستوراتش رو همه سیستم عامل ها یکیه.

پس دیگه راحت شدیم و ازین به بعد دیگه برای لینوکس و مک و ویندوز دستورات جدا در نظر نمیگیریم.

### ساخت نسخه `Release`

وقتی پروژه ات بالاخره آماده ریلیز شد، میتونی با دستور زیر پروژه ات رو کامپایل کنی و خود کارگو یه سری آپتیمیزیشن هم انجام میده واست:

```console
$ cargo build --release
```

این دستور، به جای اینکه فایل اجرایی رو داخل `target/debug` بسازه، اون رو داخل `target/release` قرار میده.

این بهینه‌سازی‌ها باعث می‌شن کد `Rust` شما سریع‌ تر اجرا بشه، ولی خب در عوض زمان کامپایل بیشتر می‌شه.

به خاطر همین `Rust` دو تا `profile` مختلف داره:

- یکی برای زمان `development`، یعنی وقتی می‌خوای سریع و پشت سر هم پروژه رو هی بیلد کنی.
- یکی برای نسخه‌ی نهایی (`release`) که میشه وقتی قراره برنامه رو به کاربر تحویل بدی، دیگه مدام بیلدش نکنی و بخوای بالاترین پرفورمنس ممکن رو بگیری.

> اگه شما داری سرعت اجرای کدت رو `benchmark` می‌کنی، حتما از `cargo build --release` استفاده کن و بنچمارکتو رو با فایل اجرایی داخل `target/release` انجام بده.

### استفاده از استانداردها و ساختار `Cargo`

برای پروژه های ساده، کارگو نسبت به اینکه مستقیم از `rustc` استفاده کنی مزیت خیلی خاصی نداره ولی هرچی برنامه‌هات بزرگ‌ تر و پیچیده‌ تر بشن، کم کم ارزشش کاملا معلوم می‌شه.

مثلا وقتی پروژه چندتا فایل داشته باشه یا به `dependency` نیاز پیدا کنه واقعا راحت تره که مدیریت اینارو کلا بسپاری به کارگو.

الان همین پروژه `hello_cargo` خودمون خیلی سادس ولی بخش زیادی از ابزار هایی که ما قراره در آینده هم استفاده کنیم رو پوشش میده.

به عبارتی، برای کار کردن روی هر پروژه‌ی `Rust` که از قبل وجود داره، شما معمولا همین دستورها رو اجرا می‌کنی:

```console
$ git clone example.org/someproject
$ cd someproject
$ cargo build
```

فعلا همینقدر بدونی کافیه و اگر اطلاعات بیشتری نیاز داری باید بری مستندات کارگو رو بخونی.
